# Архитектура MAXIMUS.BOATS
Статус: FINAL · Версия: 2.0.0 · Дата: 26 сентября 2026 года

## Границы
Проект представляет портфолио и услуги из предоставленных материалов. Это не система бронирования, CRM, инвестиционная площадка или каталог складского наличия. База данных, авторизация, платежи и вымышленные live-интеграции не добавлялись.

## Слои
Контент → сборочные компоненты → HTML. Общая валидация → браузерная форма и серверная граница доверия. Серверный обработчик → проверка Turnstile → адаптер почтового провайдера. Секретная конфигурация не передаётся в браузер.
Секции разделены на самостоятельные HTML-компоненты. Спецификации моделей вынесены в JSON и используются одинаково на главной и в отдельных досье. Локализованные данные атрибутов разрешаются при сборке. Клиентские модули добавляют только поведение; основное содержимое уже находится в HTML.

## Маршруты
Две главные страницы, восемь страниц моделей и два уведомления о конфиденциальности. Дополнительно создаются корневая страница и 404. Для моделей не требуется клиентская маршрутизация. Вкладки главной имеют ARIA-связи и клавиатурную навигацию.

## API
GET `/api/contact` возвращает режим и только открытый site key, когда он настроен.
POST: проверка метода и конфигурации → точное совпадение Origin → тип JSON → ограничение фактического размера тела → валидация полей и согласия → UUID → проверка CAPTCHA, hostname и action → фиксированный адрес получателя → ответ о принятии или ошибке.
Получатель задаётся на сервере из `site.js`; посетитель не может назначить произвольного получателя. Его email используется только как reply-to. Передача провайдерам тестируется через внедряемую fetch-функцию, без реальных писем.

## Решение по стеку
Использован предрендеринг на Node.js без npm-зависимостей, нативные ES modules и CSS. Для этого контентного сайта не требуется гидратация всего дерева интерфейса. Компромисс — собственный небольшой сборщик и ручной rebuild вместо framework hot reload. Проверка синтаксиса не объявляется проверкой TypeScript.

## Эксплуатационные ограничения
Между serverless-инстансами не используется фиктивный in-memory rate limiter. Edge rate limiting настраивается при публикации. Записи запросов приложением не сохраняются; сроки хранения почты и инфраструктурных журналов устанавливает оператор. Подключение CRM или бронирований требует отдельной модели данных и разграничения доступа.
